                                                          *autocorrect-intro*
1. INTRODUCTION~

nvim-autocorrect expands lowercase misspellings using native insert-mode
abbreviations. It includes 1,031,439 typo mappings and defaults to Markdown and
Git commit buffers. No external dictionaries are needed while editing.

Requires a recent Neovim with vim.uv, vim.system, and Lua abbreviation mappings.
Tested on Neovim v0.13.0-dev-1536+g050fa30632. Vim is not supported.

Corrections apply to whole lowercase keyword tokens by default, respecting
'iskeyword'. Initial-capital correction is opt-in; mixed-case words, acronyms,
and embedded typo suffixes remain protected. Markdown code is excluded except
recognized comments in labeled fences; other filetypes except text and
gitcommit correct only recognized comments. See
|autocorrect-context|. Existing text is not rewritten on save.

The dictionary is partitioned and read on demand. Buffers share its cache.
During insertion, at most two internal abbreviations are installed. Existing
user abbreviations take precedence. Normal mode retains no plugin abbreviations.

Loading the plugin enables the defaults. No setup call or installation hook is
required. On first load, a background Neovim process builds the dictionary under
stdpath("cache")/nvim-autocorrect/. Correction begins when that build finishes;
text typed earlier stays unchanged. Later sessions reuse the cache. Source or
builder changes trigger rebuilding on the next plugin load. The checkout may
be read-only. Run make build to prepare the cache before opening an editor.

                                                  *autocorrect-configuration*
2. CONFIGURATION~

*autocorrect.setup()*

Configure the plugin from Lua: >lua

  require("autocorrect").setup({
    filetypes = { "markdown", "gitcommit", "text" },
  })
<
filetypes~
Type: List of strings
Default: { "gitcommit", "markdown" }

Replaces the enabled filetypes. An empty list disables corrections. Calling
setup() repeatedly replaces the configuration and does not duplicate hooks.
Calling setup() with no arguments restores defaults.

To enable comments in programming filetypes, add them explicitly: >lua

  require("autocorrect").setup({
    filetypes = { "markdown", "gitcommit", "text", "lua", "python" },
  })
<
                                                    *autocorrect-context*
Context detection~

Markdown skips backtick code spans and indented code. Inside backtick/tilde
fences labeled with a language, recognized comments can be corrected while
code and strings stay unchanged. Both the Markdown and embedded-language
Tree-sitter parsers, plus Markdown language injection queries, are required.
For example, a python or bash fence can correct "# definately" to
"# definitely". Only markdown needs to be enabled in filetypes; this does not
enable correction in standalone Python or Bash buffers.

Unlabeled fences, unavailable injections/parsers, and fenced blocks with parse
errors stay unchanged. Error recovery can mistake an unfinished string for a
comment, so the injected tree must parse cleanly. Syntax highlighting alone
does not authorize comments in fences. Closing the fence is not required;
comments can qualify as soon as its contents parse successfully.

Unclosed inline spans stay protected while typing. Delimiter tracking works
without a parser or syntax highlighting; cached line states are invalidated
when text changes. Embedded parsing runs only when a candidate is inside a
fence, preserving the ordinary prose path. Tree-sitter distinguishes indented
code from nested prose
when a Markdown parser is available. Without it, lines starting with four
spaces or a tab are conservatively excluded, including indented list prose.

For all other filetypes except text and gitcommit, correction requires a
recognized comment. Tree-sitter is preferred and does not require highlighting
to be enabled. When a parser is unavailable or fails, existing Vim syntax
groups identifying comments are used. The plugin does not enable syntax or
install parsers. Without either detector, these buffers are left unchanged.
Strings (including docstrings) and executable code are excluded.

Backtick spans and backtick/tilde fenced examples in comments are excluded,
including unfinished delimiters and consecutive comment lines. Existing case
and identifier protections still apply. Recognizable URL/email tokens are
excluded in Markdown and comments; Markdown link destinations are excluded
too. This is delimiter-based protection, not a complete Markdown parser or a
classifier for unmarked code examples. An unmatched backtick can suppress
correction until its matching delimiter or a blank line.

The text and gitcommit filetypes retain whole-buffer correction. Existing
user abbreviations remain authoritative and are not restricted by these checks.

correct_capitalized~
Type: Boolean
Default: false

Opt in to documented initial-capital corrections: >lua

  require("autocorrect").setup({ correct_capitalized = true })
<
For example, "Definately" becomes "Definitely" and "Recieve" becomes "Receive".
The 29,438 eligible mappings must already be accepted lowercase corrections,
documented by codespell or reviewed evidence, with at least six input letters
and a single-word destination. Only one initial ASCII capital followed by
lowercase ASCII letters qualifies. All-caps, mixed-case words, short inputs,
and joined phrases remain excluded: "DEFINATELY", "DeFinately", "Wiht", and
"Eachother" stay unchanged. Known names remain protected; unlisted names and
brands can still collide with documented typos. This option applies in eligible
prose and comments, without sentence-start detection.

*g:nvim_autocorrect*
Type: Dictionary
Default: {}

Options passed to setup() when the plugin loads. Set before loading the plugin.
A prior setup() call takes precedence. To change configuration after loading,
call setup() again.

                                                       *autocorrect-commands*
3. COMMANDS~

:AutocorrectBuild                                          *:AutocorrectBuild*

  Rebuild the local cache from data/corrections.json in a separate headless
  Neovim process. Reload the result when complete. A loaded dictionary remains
  usable during the build. Errors are reported without replacing good data.
  Concurrent requests are queued so the final source state wins.

  Saving the plugin's data/corrections.json or data/capitalized-corrections.json
  automatically triggers this command's rebuild behavior. Files with the same
  name elsewhere do not trigger it.

                                                       *autocorrect-mappings*
4. MAPPINGS~

No default key mappings are provided. Native abbreviation controls apply:

  Separator   Expand a matching word and insert the separator.
  CTRL-]      Expand without inserting a separator.
  CTRL-V      Quote the next separator to bypass its expansion.
  Escape      Expand a matching complete token when leaving Insert mode.

Escape and CTRL-] preserve a token when keyword characters follow the cursor.
Undo/redo and macros follow native abbreviation behavior. See |abbreviations|.

                                                     *autocorrect-dictionary*
5. DICTIONARY~

Edit data/corrections.json in the plugin directory. Keys are correct spellings;
values are explicit arrays of accepted typos. Example subsets: >json

  {
    "definitely": ["definately"],
    "separately": ["seperately", "sepparately"]
  }
<
Inputs must be lowercase ASCII words. Destinations may contain one or two
lowercase ASCII words separated by exactly one space. Apostrophes and other
punctuation remain excluded. Keep keys and typo lists sorted, with
one typo per line. Empty lists, duplicate keys or typos, conflicting corrections,
and mappings to the same word fail the build. An empty object disables all
mappings. See CONTRIBUTING.md for editing conventions and validation details.

From the plugin repository, run:

  make build                  Build the local cache and print its path.
  make check                  Build, validate, and test from a fresh checkout.
  make benchmark              Measure editing with the shipped dictionary.
  make benchmark-dictionary   Measure bucket loading and retained memory.

Commit the source and refreshed data/audit.json; generated caches are not tracked
in Git. See CONTRIBUTING.md for cache details, source credits, and the separate
linguistic audit. An old data/dictionary.mpack in the checkout is unused.

Screening protects known words, names, and corpus tokens before ranking any
correction. It cannot protect every unlisted lowercase name or specialized term.

A unique adjacent-letter swap takes precedence over alternatives that delete
one letter: "requirse" becomes "requires", taking precedence over "require".
At five or more letters, a unique swap can also beat same-length non-swap
alternatives with a 100-fold frequency lead and at least 10 occurrences per
million. This admits "hwere" to "where" despite "twere"; shorter "here" and
"were" retain their existing treatment. Independently documented swaps such as
"wehther" to "whether" need only a strict frequency lead over each same-length
alternative, with the same 10-per-million floor and five-letter minimum.
Longer candidates and multiple swaps block the swap preference. The documented
rule adds 133 corrections; the earlier frequency refinement added 899.
When this cannot resolve an ambiguity, the most frequent candidate can win if
it occurs at least 10 times per million words and is at least 100 times more
frequent than every alternative. For example, "abotu" becomes "about". Close
alternatives remain uncorrected. Frequencies are a heuristic for user intent.

Five-letter swaps such as "mgiht" to "might" may qualify under these preferences;
other five-letter edits require documentation or a common-word rule.
Typos of three/four-letter words, such as "wiht" to "with", qualify when the
word occurs at least 100 times per million and leads every alternative by at
least 100-fold. Inputs may have three to five letters; shorter inputs remain
excluded. This adds 7,010 corrections, including extra-keystroke errors.

Four/five-letter keyboard typos of common five-letter words also qualify at
100 occurrences per million and a 100-fold lead over all alternatives. This
admits "whch", "whih", and "wgich" to "which", with protection and the existing
candidate-selection order intact.

data/reviewed-corrections.json supplements codespell with exact pairs and source
evidence. Examples include "probebly" to "probably", "rimember" to "remember",
and "thousend" to "thousand". Documented swaps "peolpe" and "pepole" to "people"
can also pass corpus screening. Evidence does not override protected input or
ambiguity checks. The common-word/evidence batch adds 2,026 corrections.
After changing evidence, refresh the catalog and audit together; make check
verifies the evidence hash. This file is not read during editing.

data/capitalized-corrections.json is the derived initial-capital subset. It is
compiled into the same lazy dictionary buckets; it adds no Python dependency
at installation or while editing. See CONTRIBUTING.md for regeneration.

"hte" to "the" is an exact, reviewed, codespell-confirmed exception to length
and ambiguity rules. No exception overrides protected input or case and
boundary checks: "trial", "trail", "HTE", and "Hte" stay unchanged. Short-word
screening also leaves "wth", "teh", and ambiguous "fomr" unchanged.
Eleven documented joined words, including "eachother" to "each other", "fromthe"
to "from the", and "wantto" to "want to", restore a missing space. The input must
have at least six letters, both components must be SCOWL words occurring at
least 100 times per million, the split must be unique, and no known single-edit
word may compete. The audit records these separately as joined_word_corrections.
Protected tokens such as "alot", "aswell", "dont", "didnt", and "isnt" remain
unchanged. Apostrophe restoration is excluded by the current protection policy.
See CONTRIBUTING.md for the complete selection rules.

data/protected-words.json supplements the reference dictionaries with documented
legitimate terms such as "buidl". These tokens cannot be corrected and also count
as competing candidates. Entries require a reason and source URL. After changing
the list, refresh the catalog and audit, rebuild, and reload the dictionary; the
list is maintenance input, not read during editing. See CONTRIBUTING.md for the
full workflow. make check verifies the audit's supplemental-list hash too.
